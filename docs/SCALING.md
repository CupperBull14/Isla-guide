# Масштабирование: от 1 до 1000+ посетителей

## Почему сайт уже переносит нагрузку
Это статический сайт: HTML/JS/CSS отдаёт CDN хостинга, на каждый визит нет ни сервера, ни базы. 1000 одновременных посетителей — это 1000 раз скачать ~200 КБ (gzip) файлов с CDN; узкого места на нашей стороне нет. Файлы Vite имеют хэши в именах → браузер кэширует их надолго.

## Мягкие лимиты хостинга (сверять с их текущей документацией)
- GitHub Pages: ориентир ~100 ГБ трафика в месяц, ~1 ГБ размер сайта, ограниченное число сборок в час. Хватает на десятки тысяч визитов в месяц.
- При упоре в лимит — перенос на Cloudflare Pages / Vercel / Netlify (конфиги SPA-маршрутизации уже есть). Код не меняется, меняется только `VITE_BASE` (для корня домена — `/`).

## Метрики-триггеры → действие
| Триггер | Действие |
|---|---|
| Основной JS-чанк > ~700 КБ (gzip > ~200 КБ) | Разделить данные: `import()` по виду (`getDinosaur(id)` асинхронно), главная не должна тянуть все данные |
| Видов > ~60 или файлов данных > ~1 МБ суммарно | Вынести данные в JSON в `public/data/` + загрузка по требованию, схемы сохранить в `types` |
| Нужен трафик из поиска | Пререндер (vite-ssg или аналог): страницы динозавров получат настоящий HTML |
| Нужны правки без пуша / несколько редакторов | Headless CMS или Git-based CMS; формат данных уже типизирован |
| Нужны отзывы/комментарии/счётчики | Отдельный сервис (форма → GitHub Issue, GoatCounter/Plausible для аналитики); не усложнять фронт сервером без нужды |
| Lighthouse < 90 на мобильном | Профилировать: шрифты (preload, `font-display`), картинки (WebP), `Particles` (отключить на слабых устройствах) |

## Что уже сделано для производительности
Ленивая загрузка страниц (`lazyPage`), отдельные чанки react/framer-motion, хэшированные ассеты, `prefers-reduced-motion`, canvas-частицы только на главной и с паузой на скрытой вкладке.

## Как расти, не ломая старое
1. Рост данных — это добавление файлов по образцу (см. ARCHITECTURE «Как добавить…»), а не правка движка.
2. Любое изменение формата данных — сначала опциональное поле, потом миграция всех файлов, потом (по желанию) обязательное.
3. Перед релизом — `npm run verify`; CI уже запускает `npm run check` на каждом пуше.
4. Тяжёлые правки (смена роутинга, хостинга, структуры данных) — в отдельной ветке и через ADR в `DECISIONS.md`.

## Мониторинг (по мере роста)
Добавить анонимную аналитику (GoatCounter/Plausible) — понять, какие страницы и инструменты используют; ориентироваться на данные, а не на догадки. Ссылка «Нашёл ошибку» (GitHub Issue) — канал обратной связи от игроков.
